## 2. 구성 요소 및 역할 정의

### 2.1 CIS (SAP Cloud Identity Services) — Proxy 역할

CIS는 **IdP와 SP의 이중 역할**을 합니다.

| 관점 | CIS의 역할 | 상대 시스템 |
|---|---|---|
| SAP S/4HANA 입장 | **IdP** (인증 제공자) | S/4HANA는 CIS를 신뢰 |
| Knox 입장 | **SP** (서비스 제공자) | Knox는 CIS를 신뢰 |

CIS는 단순 pass-through가 **아닙니다**. Knox에서 받은 SAML Assertion을 검증한 후 S/4HANA가 이해할 수 있는 형태로 **재발급**합니다. 즉, 두 개의 독립적인 SAML 세션을 운영합니다.

### 2.2 SLS (SAP Secure Login Service for SAP GUI)

| 항목 | 내용 |
|---|---|
| **유형** | SAP BTP 클라우드 서비스 (SaaS) |
| **역할** | **SAML 인증 결과를 SAPGUI가 이해하는 SNC X.509 인증서로 변환하는 브리지** |
| **구체적 동작** | CIS를 경유한 Knox SAML 인증이 성공하면, 해당 결과를 바탕으로 **사용자별 단기 X.509 인증서**를 실시간 발급 |
| **인증 방식** | CIS로 인증 위임 → 인증 성공 시 X.509 인증서 발급 |
| **인증서 유효기간** | 기본 12시간 (비내보내기) |
| **SAP SSO 3.0 대체** | SAP SSO 3.0은 **2027년 12월 31일 유지보수 종료** |
| **Cloud Connector** | **불필요** (SAPGUI → SAP Backend는 직접 SNC/X.509 경로) |

**핵심 개념:** SAML 메타데이터에 포함된 X.509 인증서는 **시스템 간 신뢰**(서명/암호화)를 위한 것이지만, SAPGUI가 필요로 하는 X.509 인증서는 **개별 사용자 식별**을 위한 것입니다. SLS는 이 둘을 연결하는 변환 레이어입니다.

```
Knox 인증 (SAML) → CIS 검증 → SLS → SNC X.509 사용자 인증서 발급 → SAPGUI
```

### 2.3 Knox — Corporate IdP

| 항목 | 내용 |
|---|---|
| **역할** | 최종 인증 제공자 |
| **프로토콜** | SAML 2.0 |
| **MFA** | Knox 레이어에서 enforcement (SLS/CIS/SLC/SAPGUI는 MFA 미인지) |

### 2.4 구성 요소 요약

| 구성 요소 | 위치 | Fiori/WebGUI 사용 | SAPGUI 사용 |
|---|---|---|---|
| **Knox** | Corporate IdP | ✅ | ✅ |
| **CIS (IAS)** | SAP BTP | ✅ (Proxy) | ✅ (Proxy) |
| **SLS** | SAP BTP | ❌ | ✅ (SAML→SNC X.509 변환 브리지) |
| **SLC** | End User Desktop | ❌ | ✅ |
| **SAP S/4HANA** | On-Premise | ✅ (SAML SP) | ✅ (SNC/X.509) |
| **Cloud Connector** | — | 필요 (온프레미스 접근 시) | ❌ |

## 3. 인증 흐름 — Fiori / WebGUI

### 3.1 SP-Initiated SSO (표준 흐름)

```
1. 사용자 → Fiori Launchpad 또는 WebGUI URL 접속 (브라우저)
2. S/4HANA (SAML SP) → CIS 로 SAML AuthnRequest 전송
3. CIS (IdP 역할) → CIS (SP 역할) 내부 전달
4. CIS (SP 역할) → Knox 로 SAML AuthnRequest 전송
5. Knox → 사용자 인증 (ID/PW + MFA)
6. Knox → CIS 로 SAML Assertion POST (ACS URL)
7. CIS → Assertion 검증 → S/4HANA가 이해하는 SAML로 재발급
8. S/4HANA → 세션 생성 → 접근 허용
```

### 3.2 ACS URL 요약

| 시스템 | ACS URL |
|---|---|
| **S/4HANA → CIS** | `https://<tenant>.accounts.ondemand.com/saml2/sp/acs/...` (CIS 메타데이터 XML 참조) |
| **Knox → CIS** | 동일 (CIS의 ACS 엔드포인트) |

### 3.3 CIS에서 등록할 애플리케이션

CIS Admin Console에서 **1개의 SAML 2.0 B2E 애플리케이션**을 등록합니다.

| 설정 항목 | 값 |
|---|---|
| **Application Name** | 예) `S4HANA-PRD` |
| **SP Entity ID** | T-Code `SAML2`에서 생성된 Entity ID |
| **ACS URL** | `https://<sap-host>/sap/public/bc/sec/saml2/acsp` |
| **SP Certificate** | T-Code `SAML2`에서 생성된 서명 인증서 |
| **NameID Format** | `emailAddress` (Knox와 협의) |
| **Default IdP** | Knox (Corporate IdP) |

## 4. 인증 흐름 — SAPGUI

### 4.1 전체 인증 시퀀스

```
1.  User → SAPGUI 실행
2.  SAPGUI → SAP Backend 연결 요청 (SNC 인증 필요)
3.  SLC → SLS (BTP) 에 X.509 인증서 요청
4.  SLS → CIS 로 인증 위임
5.  CIS → Knox 로 SAML AuthnRequest 전송
6.  Knox → User 인증 (ID/PW + MFA)
7.  Knox → CIS 로 SAML Assertion 전송
8.  CIS → SLS 로 인증 결과 전달
9.  SLS → 단기 X.509 인증서 발급 (기본 12시간, 비내보내기)
10. SLC → SAPGUI 에 인증서 제공
11. SAPGUI → SAP Backend 로 SNC/X.509 인증
12. SAP Backend → STRUST 에서 SAP Cloud Root CA 로 인증서 검증
13. 인증 성공 → SAPGUI 세션 시작
```

### 4.2 핵심 포인트

- **인증서 유효기간**: 기본 12시간 또는 User 로그오프 시 만료
- **SAP Backend → 클라우드 연결**: 불필요
- **MFA 발생 위치**: Step 6, Knox 레이어에서만 enforcement
- **SLC 내장 browser**: Knox 로그인/MFA 화면이 SLC 내장 hardened browser에서 자동 표시 — 별도 개발 불필요

## 5. CIS vs SLS vs Kerberos — 비교 및 선택

### 5.1 프로토콜 비교

| 구분 | SAPGUI | Fiori | WebGUI |
|---|---|---|---|
| **접근 방식** | 클라이언트 앱 (RFC/SNC) | 웹 브라우저 (REST/OData) | 웹 브라우저 (HTTP) |
| **SAML 2.0 직접 지원** | ❌ | ✅ | ✅ |
| **주요 SSO 방식** | SLS (X.509) 또는 Kerberos | SAML 2.0 (CIS 경유) | SAML 2.0 (CIS 경유) |
| **CIS 연동 방법** | SLS 브리지 필요 | 직접 SAML SP 연동 | 직접 SAML SP 연동 |

### 5.2 SAPGUI SSO 옵션 비교

| 항목 | Kerberos | SLS (X.509) | Logon Ticket |
|---|---|---|---|
| **AD 필요** | ✅ 필수 | ❌ | ❌ |
| **MFA 지원** | ❌ (AD MFA 의존) | ✅ (Knox MFA) | ❌ |
| **원격 접속** | ❌ (도메인 네트워크 필요) | ✅ | ⚠️ (Portal 필요) |
| **CIS 연동** | ❌ | ✅ | ❌ |
| **권장** | 사내 AD 환경만 | **본 프로젝트 권장** | 레거시 |

### 5.3 본 프로젝트 권장 구성

| 접근 방식 | 인증 방식 |
|---|---|
| **Fiori** | SAML 2.0 → CIS → Knox |
| **WebGUI** | SAML 2.0 → CIS → Knox |
| **SAPGUI** | SLS → CIS → Knox (X.509) |

## 6. 단계별 설정 가이드

### Phase 1: SAP S/4HANA 백엔드 — SAML SP 활성화

**T-Code `SAML2`**가 SAML 2.0 Service Provider 설정의 실제 트랜잭션 코드입니다.

1. **T-Code `SAML2`** 실행
2. 최초 실행 시 "Client X is not configured to support SAML 2.0" 메시지 → **Enable SAML 2.0 Support** 클릭
3. **SP 이름** 입력 (예: `S4HANA-SP`)
4. 설정 마법사 진행:
   - **Signing PSE** 생성 (서명용 키 쌍)
   - **Encryption PSE** 생성 (암호화용 키 쌍)
   - Entity ID 자동 생성
5. **Finish** 클릭
6. **ICF 서비스 활성화** (T-Code `SICF`):
   - `/default_host/sap/public/bc/sec/saml2` → 활성화
   - `/default_host/sap/public/bc/sec/cdc_ext_service` → 활성화
7. 생성된 **Entity ID**, **ACS URL**, **서명 인증서** 기록 (CIS 등록용)

> **출처**: SAP Help Portal — [Enabling the SAML Service Provider](https://help.sap.com/docs/ABAP_PLATFORM_NEW/e815bb97839a4d83be6c4fca48ee5777/4ab4c93185376d61e10000000a42189c.html)

---

### Phase 2: CIS — Knox를 Corporate IdP로 등록

1. CIS Admin Console 로그인
2. **Identity Providers** → **Corporate Identity Providers** → **Create**
3. 설정:
   - **Display Name**: `Knox`
   - **Identity Provider Type**: `SAML 2.0 Compliant`
4. **SAML 2.0 Configuration** → Knox 메타데이터 XML 업로드 또는 수동 입력:
   - **Name**: Knox Entity ID
   - **Single Sign-On Endpoint URL**: Knox SSO 엔드포인트
   - **Signing Certificate**: Knox 서명 인증서
   - **Digest Algorithm**: `SHA-256`
5. **Identity Federation** → **Use Identity Authentication user store** → **ON** (Corporate IdP Attribute 참조 필수)
6. 저장

---

### Phase 3: CIS — S/4HANA 애플리케이션 등록 (Fiori / WebGUI용)

1. **Applications and Resources** → **Applications** → **Create**
2. **Application Type**: `SAML 2.0 B2E`
3. 설정:
   - **Application Name**: `S4HANA-PRD`
   - **SP Entity ID**: Phase 1에서 생성된 Entity ID
   - **ACS URL**: `https://<sap-host>/sap/public/bc/sec/saml2/acsp`
   - **SP Certificate**: Phase 1에서 생성된 서명 인증서 업로드
4. **Trust** 탭:
   - **Conditional Authentication** → Knox 선택 (Default IdP)
   - **Attributes** → 필요 속성 매핑 설정
5. 저장

---

### Phase 4: Knox — CIS를 SP로 등록

Knox 관리 콘솔에서 CIS를 Relying Party / SP로 등록합니다.

| Knox 설정 항목 | CIS에서 가져올 값 |
|---|---|
| **SP Entity ID** | `https://<tenant>.accounts.ondemand.com/saml2` |
| **ACS URL** | `https://<tenant>.accounts.ondemand.com/saml2/sp/acs/...` (CIS 메타데이터 XML 참조) |
| **SP Certificate** | CIS Tenant SAML 2.0 Configurations에서 다운로드 |
| **NameID Format** | CIS 설정과 일치 (`emailAddress`) |
| **Attributes** | `uid`, `email`, `displayName` 등 |

---

### Phase 5: S/4HANA — CIS를 신뢰하는 IdP로 등록

1. **T-Code `SAML2`** → **Trusted Providers** 탭
2. CIS의 SAML 메타데이터 XML 업로드 또는 수동 입력:
   - CIS Entity ID
   - CIS SSO URL
   - CIS 서명 인증서
3. 저장

---

### Phase 6: BTP — SLS 서비스 구독 및 활성화 (SAPGUI용)

1. **BTP Cockpit** → Subaccount 선택
2. **Service Marketplace** → **Secure Login Service for SAP GUI** 구독
3. 서비스 인스턴스 생성
4. **Security** → **Trust Configuration** → CIS와 BTP Subaccount 간 신뢰 설정
5. **SLS Admin 역할** 할당 (`SecureLoginServiceAdministrator`)

---

### Phase 7: CIS — SLS 애플리케이션 설정

1. **Applications** → SLS 애플리케이션 선택
2. **Trust** 탭:
   - **Conditional Authentication** → Knox 선택 (Default IdP)
   - **Subject Name Identifier** 설정:
     - Corporate IdP 사용자: `${corporateIdP.loginName}` 또는 `${corporateIdP.mail}`
   - **Attributes** → `sls_common_name` 설정 (선택):
     - `sls_common_name` = `${corporateIdP.loginName}`
3. 저장

---

### Phase 8: SLS Web UI 설정

1. SLS Web UI 로그인
2. **Certificate 유효기간** 설정 (기본 12시간)
3. **Host Policy Group URL** 획득 (SLC 설정용)

### Phase 9: SAP S/4HANA — SNC/X.509 설정 (SAPGUI용)

#### 9.1 STRUST 설정

1. **T-Code `STRUST`** 실행
2. **SAP Cloud Root CA** 인증서 등록:
   - Environment → Import Own Certificate → SAP Cloud CA 인증서 등록
3. SSF 버전 확인 (Environment → Display SSF Version)

#### 9.2 SNC 설정

1. **T-Code `SNCCONFIG`** (또는 `SNCWIZARD`) 실행
2. 프로파일 파라미터 설정 (T-Code `RZ10`):

| 파라미터 | 값 | 설명 |
|---|---|---|
| `snc/enable` | `1` | SNC 활성화 |
| `snc/enable_ssl_library_trustmech` | `1` | SSL 라이브러리 신뢰 메커니즘 |
| `snc/identity/as` | `p:CN=<SAP System SNC name>` | AS SNC 이름 |
| `ccl/snc/namealias/value_1` | `, L=<CIS tenant url>, OU=secure-login-service, OU=Clients, O=SAP, C=DE` | SLS SNC 이름 패턴 |
| `ccl/snc/partner_case_x509` | `Upper` | 대문자 매핑 |
| `ccl/snc/server_partner_name_x509` | `EMailPrincipalOnlyOrSubject` | 파트너 이름 매핑 |
| `ccl/snc/server_partner_name_mapping_for_SLC` | `1` | SLC 매핑 활성화 |

3. **T-Code `RSBDCOS0`** 실행 → `sapgenpse` 명령어 확인
4. **T-Code `SSF02`** 실행
5. AS ABAP 인스턴스 재시작

#### 9.3 사용자 SNC 이름 매핑

1. **T-Code `SU01`** → 사용자 마스터 → **SNC 탭**
2. SLS 기반 인증서 형식으로 SNC Name 설정:
   ```
   p:CN=<username>,<SLS issuer domain>
   ```

## 7. MFA 적용

### 7.1 MFA 적용 위치

MFA는 **Knox 레이어에서만 enforcement**됩니다. SLS/CIS/SLC/SAPGUI는 MFA를 인지하지도, 처리하지도 않습니다.

```
SAPGUI → SLC → SLS → CIS → Knox
                                        ↓
                                 ┌──────────────┐
                                 │ ID/PW 인증    │
                                 │ MFA 정책 평가 │  ← MFA 결정 지점
                                 │ MFA 챌린지    │
                                 │ (SMS/mOTP/   │
                                 │  TOTP/생체)  │
                                 └──────────────┘
                                        ↓
                                 SAML Assertion
```

### 7.2 MFA 인증 화면 — 별도 개발 불필요

SLC 내장 hardened browser가 Knox 로그인/MFA 화면을 자동 표시합니다.

```
SAPGUI 실행
  ↓
SLC가 X.509 인증서 필요 감지 (또는 인증서 만료)
  ↓
SLC 내장 browser 자동 팝업
  ↓
Knox 로그인 화면 표시 (ID/PW 입력)
  ↓
Knox MFA 정책 평가 → MFA 필요 시 MFA 챌린지 화면 표시
  ↓
MFA 통과 → SAML Assertion → CIS → SLS → X.509 발급
  ↓
SLC가 인증서를 SAPGUI에 제공 → SAPGUI 로그인 성공
```

### 7.3 Knox 운영팀 요청 사항

1. **MFA 정책 적용** — CIS ACS URL 서비스에 MFA 정책 적용
2. **MFA 인증 방식 선택** — SMS/mOTP/TOTP/생체 등 조직 정책 기준
3. **SSO 세션 정책** — Knox SSO 세션 유효기간 및 MFA 재발생 조건
4. **조건부 MFA** — IP/기기/시간 기반 조건부 MFA 설정 (선택)

### 7.4 인증서 유효기간과 MFA 빈도

| 인증서 유효기간 | MFA 발생 빈도 | 권장도 |
|---|---|---|
| **12시간 (기본)** | 하루 1~2회 | ✅ 권장 |
| **8시간** | 하루 2~3회 | 보통 |
| **24시간** | 하루 1회 | 보안 트레이드오프 |

## 8. 방화벽 설정

### 8.1 네트워크 흐름

| 방향 | 프로토콜 | 포트 | 설명 |
|---|---|---|---|
| End User → SLS (BTP) | HTTPS (TCP) | 443 | X.509 인증서 요청 |
| End User → SAP Backend | TCP | SAP 메시지 서버 포트 | SNC/X.509 인증 |
| Browser → S/4HANA | HTTPS (TCP) | 443 | Fiori/WebGUI 접근 |
| CIS → Knox | HTTPS (TCP) | 443 | SAML AuthnRequest |
| Knox → CIS | HTTPS (TCP) | 443 | SAML Assertion (브라우저 POST) |

### 8.2 SAP BTP Neo 리전별 NAT IP (아웃바운드)

CIS에서 온프레미스 Knox로 접근 시 Knox 측 방화벽에 해당 IP를 허용해야 합니다.

| 리전 | 호스트 | NAT IP (CIDR) |
|---|---|---|
| Japan (Tokyo) | jp1.hana.ondemand.com | `157.133.182.32/27`, `130.214.244.32/27` |
| Europe (Frankfurt) | eu2.hana.ondemand.com | `130.214.228.32/27` |
| Europe (Rot) | eu1.hana.ondemand.com | `157.133.160.32/27`, `130.214.226.32/27` |
| US East (Ashburn) | us1.hana.ondemand.com | `157.133.166.32/27`, `130.214.234.32/27` |
| US West (Chandler) | us2.hana.ondemand.com | `130.214.254.32/27` |
| US West (Colorado) | us4.hana.ondemand.com | `130.214.242.32/27` |
| Australia (Sydney) | ap1.hana.ondemand.com | `157.133.168.32/27`, `130.214.240.32/27` |
| Europe (Amsterdam) | eu3.hana.ondemand.com | `157.133.170.32/27`, `130.214.230.32/27` |
| UAE (Dubai) | ae1.hana.ondemand.com | `130.214.250.32/27` |

> `/27` CIDR는 32개 IP를 의미합니다. CIS 테넌트 URL에서 리전을 확인한 후 해당 IP를 Knox 측 방화벽에 Inbound 허용 (TCP 443)합니다.
>
