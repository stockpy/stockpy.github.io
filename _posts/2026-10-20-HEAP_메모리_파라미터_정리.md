# HEAP 메모리 파라미터 정리 (abap/heap_area_*, ztta/max_memreq_MB)

## 개요

워크프로세스의 PRIV 메모리(HEAP) 관련 파라미터와 개별 세션의 메모리 요청 한도 파라미터를 정리한 문서입니다. [EM 메모리 파라미터 정리](/general/2026/10/15/EM_메모리_파라미터_정리.html)에서 다룬 `em/*`, `ztta/roll_extension*`(EM 쪽)와 대응되는 개념입니다.

- **인스턴스 전체 HEAP 총량**: `abap/heap_area_total`
- **워크프로세스(사용자 컨텍스트)당 HEAP 쿼터**: `abap/heap_area_dia`, `abap/heap_area_nondia`
- **개별 세션의 단일 메모리 요청 최대 크기**: `ztta/max_memreq_MB`

## 0. 세션(사용자 컨텍스트)과 워크프로세스의 구분

이 문서의 파라미터를 이해하려면 두 주체를 명확히 구분해야 합니다.

| 구분 | 세션 (사용자 컨텍스트, user context) | 워크프로세스 (work process) |
|---|---|---|
| 성격 | 한 사용자가 SAP에 로그인한 **논리적 연결** (OS 프로세스가 아님) | AS 인스턴스가 만드는 **OS 프로세스** (DIA/BTC/UPD/SPU 등) |
| 수 | 동시 로그인 수만큼 (예: 500명 로그인 → 500개 세션) | 프로필로 고정 (예: DIA 20개, BTC 10개) |
| 메모리 소유 | **EM** — 인스턴스가 공유하는 풀 안의 "자기 영역" | **PRIV(HEAP)** — 프로세스 주소 공간의 사적 메모리 |
| 이동 | 컨텍스트 전환으로 워크프로세스를 **자유롭게 떠다님** | 고정 (PRIV 모드 전환 시 특정 세션에 고정됨) |

**핵심**: EM은 세션의 메모리이고, PRIV(HEAP)는 워크프로세스의 메모리입니다.

- 대화형 워크프로세스는 여러 세션을 순서대로 처리합니다. 세션 A를 처리하다가 B로 전환하면, A의 EM 데이터는 공유 풀에 그대로 남아 있고 프로세스는 B의 EM을 계속 쓰면 됩니다(빠름).
- 하지만 PRIV는 프로세스 주소 공간에 있으므로, 세션 A가 PRIV(HEAP)를 많이 쓰면 전환 시 A의 데이터를 **swap으로 내보내고** B의 데이터를 swap에서 불러와야 합니다(느림).
- 그래서 대화형 워크프로세스는 **EM을 먼저, PRIV를 나중에** 씁니다.

이 구분이 모호하면 파라미터 이름이 헷갈립니다. `ztta/roll_extension*`는 **세션 단위 한도**(EM 풀 안에서 한 세션이 쓸 수 있는 최대치)이고, `abap/heap_area_*`는 **워크프로세스 단위 한도**(프로세스가 처리 중인 한 사용자 컨텍스트를 위해 쓸 수 있는 최대 PRIV)입니다. 실무에서는 대화형 WP가 1개 세션만 처리하므로 둘의 수치가 비슷하게 느껴지지만, 개념적 소유 주체는 다릅니다.

| 구분 | EM (Extended Memory) | PRIV (HEAP) |
|---|---|---|
| 소유 주체 | **세션**(사용자 컨텍스트) | **워크프로세스**(OS 프로세스) |
| 물리적 위치 | 인스턴스 전체가 공유하는 풀 | 프로세스 주소 공간의 사적 메모리 |
| 컨텍스트 전환 | 가능 (풀 안의 영역만 바꿈, 빠름) | 불가 → 전환 시 swap으로 내보내야 함 |
| 세션당 한도 | `ztta/roll_extension*` | `abap/heap_area_*` |
| 풀 전체 크기 | `em/initial_size_MB` | `abap/heap_area_total` |

즉, `ztta/roll_extension`은 "EM 풀에서 **한 세션**이 쓸 수 있는 한도"이고, `abap/heap_area_*`는 "PRIV(HEAP)에서 **한 워크프로세스**(가 처리 중인 한 사용자 컨텍스트)가 쓸 수 있는 한도"입니다.

## 1. abap/heap_area_total — 인스턴스 전체 PRIV 총량

**정의**: AS 인스턴스의 **모든** 워크프로세스(대화형 + 비대화형)가 합쳐서 할당할 수 있는 PRIV 메모리의 총 상한.

- swap 사용량을 예측 가능한 수준으로 제한해 swap 병목을 막기 위한 목적.
- `em/proc_max_size_MB`(PROC 메모리 상한)와 함께 쓰면 AS 인스턴스의 swap 사용 상한을 예측 가능.
- SAP의 설계 기준: "최대 swap 사용 시에도 swap 공간의 10~15%는 항상 남도록".

**기본값** (단위: **바이트**, PHYS_MEMSIZE는 MB):

| 플랫폼 | 기본값 공식 |
|---|---|
| Windows | `$(PHYS_MEMSIZE) * 1024 * 1024` (물리 메모리 **전체 크기**) |
| 기타 (Linux 등) | `max($(PHYS_MEMSIZE) * 1024 * 1024 * 0.1, $(abap/heap_area_dia) * 2)` (물리의 **10%**, 단 heap_area_dia의 2배 미만이면 2배로) |

**주의**: Linux 기본값 공식이 `abap/heap_area_dia`에 의존합니다. `abap/heap_area_dia`를 고정값으로 올리면 `abap/heap_area_total` 계산값이 `heap_area_dia × 2`로 함께 올라갈 수 있습니다.

## 2. abap/heap_area_dia — 대화형 WP의 PRIV 쿼터

**정의**: **1개 대화형 워크프로세스가 1개 사용자 컨텍스트에 대해** 할당할 수 있는 PRIV 메모리 크기.

- 기본값: **2,000,000,000 바이트 (약 2 GB)**
- `abap/heap_area_total`보다 작게 설정해야 합니다.
- **쿼터 초과 시 동작: 해당 ABAP 프로그램이 종료되고 short dump 발생** (EM 쿼터 초과 시의 PRIV 모드 전환과 다름).
- 참고: `abap/heaplimit`을 설정하면 쿼터에 도달하기 전에 워크프로세스가 리스타트됩니다.

## 3. abap/heap_area_nondia — 비대화형 WP의 PRIV 쿼터

**정의**: 1개 비대화형(백그라운드/업데이트/스풀) WP가 1개 사용자 컨텍스트에 대해 할당할 수 있는 PRIV 크기.

| 플랫폼 | 기본값 |
|---|---|
| 기타 (Linux 등) | 2,000,000,000 (약 2 GB) |
| Windows | **0 (쿼터 무효)** |

- Windows는 비대화형 WP의 할당 순서가 다르기 때문에(아래 4.2 참고) 기본값 0이 "EM 쿼터 초과 후 PRIV로 넘어가는 것을 `abap/heap_area_total`까지 허용"하는 방식이 됩니다.
- 비대화형 WP(특히 메모리 집약적인 백그라운드 잡)에는 충분한 PRIV를 확보해 주는 것이 좋습니다.

## 4. 프로세스별 메모리 사용 순서 (Unix/Linux 기준)

### 4.1 대화형 워크프로세스

```
① EM 할당  (한도: ztta/roll_extension_dia)
      ↓ EM 쿼터 도달
② PRIV(HEAP) 할당  (한도: abap/heap_area_dia)
      ↓ PRIV 쿼터 도달
③ ABAP 프로그램 종료 + short dump
```

- 대화형 WP는 컨텍스트 전환이 잦으므로 **EM을 먼저** 씁니다.
- EM 쿼터에 도달하지 않았더라도 **EM 풀 전체(`em/initial_size_MB`)가 가득 차면** PRIV를 할당합니다.
- EM→PRIV로 넘어간 WP는 해당 컨텍스트에 고정(PRIV 모드)되어 컨텍스트 전환이 불가능해집니다 (SM50에서 확인 가능).

### 4.2 비대화형 워크프로세스

```
① PRIV(HEAP) 할당  (한도: abap/heap_area_nondia)
      ↓ PRIV 쿼터 도달
② EM 할당  (한도: ztta/roll_extension_nondia)
      ↓ EM 쿼터 도달
③ ABAP 프로그램 종료 + short dump
```

- 비대화형은 컨텍스트 전환이 없으므로 **PRIV를 먼저** 씁니다.
- PRIV 총량(`abap/heap_area_total`)이 먼저 소진되면 EM에서 할당합니다.
- **Windows 특이사항**: 비대화형 WP는 ① EM → ② PRIV 순서로 바뀌며, `abap/heap_area_nondia` 기본값 0이 이 순서를 제어합니다.

## 5. ztta/max_memreq_MB — 단일 메모리 요청 최대 크기

중요한 구분: `ztta/max_memreq_MB`는 **세션의 총 메모리 한도가 아니라, "한 번의 요청(단일 메모리 요청)으로 가져올 수 있는 최대 크기"**입니다.

- 대상: 동적 데이터 객체 — **string/byte string**과 **내부 테이블(hash table)의 테이블 본체**
- string: 파라미터 값이 그대로 최대 크기가 됨
- hash table: 파라미터 값 ÷ 8에 들어가는 2의 거듭제곱이 최대 행 수 결정 (예: 250 MB → 약 1,677만 행)
- 초과 시: string은 catchable 예외, 내부 테이블은 **catch 불가능한 런타임 에러**

**기본값** (SAP Note 353579 기준):

| 릴리스 | 기본값 |
|---|---|
| 4.6 | 64 MB |
| 6.20 (32비트) | 250 MB |
| 6.20 이후 (64비트) | **2047 MB** |

- 최대값: 2,147,483,647 바이트(2 GB)에 해당하는 2047 MB. 그 이상 설정하면 커널이 2047로 처리하고 경고 메시지 출력.
- **SYSTEM_NO_ROLL** short dump("max. memrequest size exceeded")가 나는 경우의 표준 조치: 이 값을 늘리는 것. 단, 2 GB 초과 요청이 발생하면 파라미터 문제가 아니라 ABAP 런타임/응용의 버그로 봅니다.

`ztta/roll_extension`과의 관계:

- `ztta/roll_extension`: 한 세션이 **EM에서 쓸 수 있는 총 한도** (세션 전체)
- `ztta/max_memreq_MB`: 그 안에서 **한 번에 요청할 수 있는 최대 블록 크기** (요청 단위)

즉, 세션이 500 MB를 쓰더라도 500 MB짜리 단일 요청이 1회 발생하면 max_memreq_MB ≥ 500 MB가 필요합니다.

## 6. ECS 표준값 (SAP Note 3517086)

SAP Enterprise Cloud Services(RISE with SAP S/4HANA Cloud Private Edition) 배포 시스템의 표준값입니다. **on-premise 시스템에는 그대로 적용할 수 없습니다.**

### 6.1 abap/heap_area_total

- **Windows**: 커널 기본값(물리 메모리 전체)을 쓰지 않고, DEFAULT.PFL에서 **`$(PHYS_MEMSIZE)*1024*1024*0.1`(물리의 10%)**으로 명시 설정. 64GB VM이면 약 6 GB.
- **Linux**: 커널 계산 기본값 사용.

ECS 허용 범위(VM 크기별):

| VM | 허용 범위 (바이트) |
|---|---|
| 16 GB | 1,000,000,000 ~ 4,000,000,000 (약 1~4 GB) |
| 32 GB | 2,000,000,000 ~ 5,000,000,000 (약 2~5 GB) |
| 64 GB | 6,000,000,000 ~ 10,000,000,000 (약 6~10 GB) |
| 128 GB | 10,000,000,000 ~ 24,000,000,000 (약 10~24 GB) |
| >128 GB | PHYS_MEMSIZE의 10% |

KBA 경고: 허용 범위 밖으로 올리면 인스턴스 메모리 풋프린트가 커져 **고부하 시 OS 스와핑**이 발생 → 성능 저하 + 인스턴스 가용성 위협.

### 6.2 abap/heap_area_dia

- 커널 기본값 **2 GB 유지** 권장. "거대한 HEAP 쿼터보다 Extended Memory를 더 잘 쓰라"는 것이 KBA의 공식 입장.
- 허용 범위: 16GB VM 1~2 GB / 128GB VM 2~16 GB / >128 GB VM 2~40 GB.
- `heap_area_dia`를 건드릴 때 반드시 `heap_area_total` 계산값도 확인해야 합니다 (1절 주의사항).

### 6.3 abap/heap_area_nondia

| 플랫폼 | 커널 기본값 | ECS 표준값 |
|---|---|---|
| Linux | 2 GB | 커널 기본값 유지 |
| Windows | 0 (쿼터 무효) | **`$(abap/heap_area_dia)`로 명시 설정** — NONDIA 요청이 무제한 HEAP을 쓰지 못하게 하려는 목적 |

### 6.4 관련 파라미터

- **abap/heaplimit**: KBA는 "**절대 설정하지 말 것**". 커널 기본값(40 MB 또는 릴리스에 따라 150 MB) 유지. 세션당 HEAP 쿼터가 아니라 **WP 리스타트 트리거**이며, 높게 잘못 설정하면 HEAP이 OS에 반환되지 않고 WP에 묶인 채 남음.
- **rdisp/os_heap_for_restart**: Kernel 7.81부터 기본값 **500M**. HEAP이 이 양을 넘으면 job/task 종료 후 WP가 리스타트되어 메모리를 OS에 반환. `em/proc_alloc_type = mmap`이 활성화된 시스템에서 `abap/heaplimit`을 내부적으로 비활성화(SAP Note 3008235, 2660701).

### 6.5 ztta/max_memreq_MB

Note 3517086의 표준 파라미터 목록과 Specials 목록 **양쪽 모두에 포함되지 않습니다**. KBA의 원칙("여기에 없는 파라미터는 커널 기본값을 사용하고 명시 설정하지 마라")에 따라, ECS 시스템에서는 이 파라미터를 **설정하지 않는 것**이 표준입니다. 기본값과 SYSTEM_NO_ROLL 대응은 SAP Note 353579가 근거입니다.

## 7. 권장 수치 추산 방법

SAP 공식 문서에 "이 공식대로 설정하라"는 단일 공식은 없고, 기본값 공식 + 운영 데이터 기반 튜닝 원칙이 제공됩니다.

### 7.1 기본값(자율 관리) 공식 모음

| 파라미터 | 공식 (64비트) |
|---|---|
| `em/initial_size_MB` | `min(512000, PHYS_MEMSIZE × 0.7)` MB (Kernel 7.85 PL 62부터 `PHYS_MEMSIZE × 0.8`) |
| `ztta/roll_extension` | Linux 4 GB / 기타 2 GB (바이트) |
| `abap/heap_area_total` | Windows: 물리 메모리 전체 / 기타: `max(물리 × 10%, heap_area_dia × 2)` (바이트) |
| `abap/heap_area_dia` / `_nondia` | 2 GB (바이트, Windows nondia = 0) |
| `ztta/max_memreq_MB` | 64비트 2047 MB |

### 7.2 운영 데이터 기반 튜닝 원칙

**① EM 쿼터 (`ztta/roll_extension*`)**
- ST02 / SM50에서 실제 세션당 최대 EM 사용량 확인 → 관찰된 최대치에 여유(약 1.2~1.5배, 실무 관례)를 두어 설정
- 제약: `em/initial_size_MB` ≥ `ztta/roll_extension` × **10~15** (EM 풀이 쿼터의 10~15배여야 컨텍스트 전환이 빠름)
- 너무 크면 큰 세션 하나가 EM을 독점 → 다른 세션의 조기 PRIV 전환 병목

**② HEAP 쿼터 (`abap/heap_area_dia` / `_nondia`)**
- "전형적인 메모리 요구를 충족할 만큼 충분히 크되, OS swap 한도보다 작게" (SAP Help 원문)
- 실용적 접근: EM 쿼터 초과 후 PRIV로 넘어가는 세션의 실제 PRIV 사용량(ST02에서 세션별 EM/HEAP 사용량 확인) 관찰 → 최대치에 여유를 더해 설정
- ECS(KBA 3517086) 입장은 기본값 2 GB 유지 + EM을 더 잘 쓰라는 것
- `abap/heap_area_dia` < `abap/heap_area_total` 필수
- `abap/heaplimit`을 함께 쓰면 쿼터 도달 전에 WP 리스타트로 short dump 대신 "정지 후 재시작"으로 처리 가능

**③ HEAP 총량 (`abap/heap_area_total`)**
- 기본값 공식이 이미 "swap의 10~15%를 항상 남긴다"는 기준으로 설계됨
- 수동 설정 시: 예상 동시 PRIV 사용량(대화형 WP 수 × heap_area_dia + 비대화형 WP 수 × heap_area_nondia)이 이 값을 초과하지 않는지, OS swap 여유와 대조

**④ `ztta/max_memreq_MB`**
- 기본값(64비트 2047 MB)에서 **SYSTEM_NO_ROLL이 실제로 발생했을 때만** 조정
- short dump의 "Unable to fulfil request for N bytes"에서 N을 확인 → N/1MB 이상으로 상향 (최대 2047)
- 2 GB 초과 요청이면 파라미터 증대가 아니라 프로그램/런타임 문제

### 7.3 파라미터 간 제약 관계 요약

```
em/initial_size_MB  ≥  ztta/roll_extension × 10~15
ztta/roll_extension <  em/initial_size_MB
abap/heap_area_dia / _nondia  <  abap/heap_area_total
abap/heap_area_total  ≤  OS swap 한도 (10~15% 여유 유지)
ztta/max_memreq_MB  ≤  2047 MB
```
